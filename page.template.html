What it is

The Forge turns a file into a picture that carries it. The file can be a web page, a report, a small app, the log of an automated run — anything that is one file of text. The picture is an ordinary PNG: it shows in any viewer, and you can post it, email it or drop it into a chat.

Inside, in two named slots every PNG is allowed to carry, sit the file (compressed) and a short label. The label holds the file's seal, a fingerprint of its exact bytes, and a signature from the key of whoever made the card. Anyone who has the picture can drop it on this page: it works the fingerprint out again from the bytes it actually holds, checks the signature, and tells you whether the file is exactly what was signed. Change one byte and it says so, and refuses to open it.

Nothing is hidden in the picture, nothing is uploaded, and nothing runs until you click. Everything on this page happens in your browser. The format is published in full in CARD-SPEC.md.

Forge one

Type anything below. It gets compressed, sealed with a hash, and tucked inside a real PNG.

You don't pick the tier — the build earns it. A build that passes the sovereignty gate (a real document, nothing reaching outside your device, the architecture line) is uncommon; anything else is common. Deeper tiers come only from a proven lineage, and anyone who opens the card re-checks this for themselves. Every card is signed with this browser's own key.

The tier is worked out, not chosen. There is no control for it: the sovereignty gate runs on the build when the card is forged, and every reader runs it again on what comes out. A build that fails it is common however deep its lineage, and a card whose label claims more is called an overclaim. That is the whole point of a card: you cannot claim a grade, only earn one.

The seal you can read

Post a card and the platform may strip its build out, or turn it into a JPEG. The picture survives. So every card now prints the first 80 bits of its seal on its face, in a band anyone can read.

Two people holding the same card is what makes a stripped copy whole. The copy keeps the printed seal; whoever holds the card keeps the build. Drop the stripped copy here, the page reads the band off the pixels, finds the card in your deck, and re-checks the build against its full seal. The picture only says which card it is. What comes out is always your own copy, verified.

Made to be read back exactly. A sealed test had a vision model read 64 rendered texts blind (kar-pixel-cost). Every miss was one character, never a word: O read as 0, C as c, a curly quote straightened, an extra digit in a hex run, a long run miscounted. So the band uses Crockford base32, which has no I, L, O or U and is read case-blind. It prints in groups of four, so there are no long runs. Its blocky 5×7 letters all differ from each other in at least five dots. A read is matched to your deck by edit distance: a slip is corrected, and a read that could be two cards is refused, never guessed.

Nothing is hidden. The band is printed in plain sight, like a serial number, and carries only the seal. The build still rides in the named chunks, and the picture's own data is never used to smuggle anything.

Why it cannot be faked

The seal is a hash of the compressed build. Change one byte of what is inside and the seal stops matching, and this page tells you so. Nobody has to be trusted — the check is re-run in front of you, on your own machine.

It is still a real PNG. The build rides in the text chunks every PNG is allowed to carry, so a picture viewer shows a picture and ignores the rest. Nothing is hidden or smuggled — the chunks are named, and the whole point is that anybody can look.

Nothing leaves your browser. Compressing, hashing and reading all happen here. There is no server to send it to.

The fold teaches the structure, not its truth. A crease pattern that closes earns its tier by geometry — the medium physically cannot draw an apex at the center. Whether the structure folded into it is TRUE is a separate question the card never claims to settle.

Blueprint

The organs, one file each, zero dependencies. Which tests guard each one and how it is gated are read from the repository when this page is built — the test files and .github/workflows/gate.yml.

What "mutation-gated" means here. On every push, GitHub's runner fetches a pinned copy of witness, flips one operator at a time in the organ (< to <=, && to ||, === to !== …) and runs that organ's tests against each change. Every change must make a test fail. One that does not is a line no test really checks, and the push goes red. A change that cannot alter behaviour may be excused only with a written reason, kept in the repository beside the code.

Adoption

What it does for a team, and how a team starts using it.

What it does. Any file a team sends out — a report, a release, a dashboard, a quote, the log of an automated run — goes out as a card. Whoever receives it checks it themselves, in seconds, with no account and no server: it is exactly what was signed, by the key that signed it, or it is refused. Copies keep that property wherever they travel, and a copy a platform stripped still finds its build in the receiver's deck.

Where it fits first.

  • Hand-offs where "is this the version we approved?" costs a phone call: client deliverables, sign-offs, board packs.
  • Results from automated runs and AI agents, sealed as they finish, so an edited copy of the result is caught by anyone who reads it.
  • Small internal tools passed around as files: the tool and its proof travel together, and it opens sandboxed.

Rolling it out.

  1. Pick one recurring file a team already sends — a weekly report, release notes, a run log — and one team that receives it.
  2. Seal it where it is made. In the browser, on this page; in a build or a scheduled job, with node forge.mjs forge --build report.html --art --out report.png. Each person or machine has its own key (~/.fallkard/identity.json, made on first use).
  3. Publish the public keys of the people and machines whose cards count, somewhere the team already trusts — an intranet page, the repository.
  4. Check it where it lands. Receivers drop it on this page or on the saved standalone reader; a pipeline runs node forge.mjs read card.png and stops on a non-zero exit.
  5. Measure it with the cost case below, using your own counts from the pilot, then widen it to the next file.

Everything runs from the files in the repository: the page is one HTML file, the reader is one HTML file, the command line is Node with no packages. A team can host its own copy on its own origin, which also gives its builder keys an origin no other page shares.

Security and data protection.

  • Nothing is uploaded. Forging, reading and checking run in the browser; the page has no server and collects nothing. Cards you open are kept in this browser's own storage (the deck), and you can clear it with one button.
  • Two optional features reach out, and say so. Trade one can use a public STUN server to find a route between networks; it sees your IP address and no card. The studio's generator sends your own prompt with your own Anthropic key straight from your browser to Anthropic. Both are off unless you use them; Trade's STUN can be unticked.
  • Keys. Each browser's signing key is made non-extractable and kept in IndexedDB: the page can ask it to sign but can never read it out. Other pages on the same origin could also ask it to sign — host your own copy for an origin of your own. The command line keeps its key in a file only you can read.
  • A card is untrusted input. Its text is escaped before it reaches the page, its build inflates only up to a cap, and the build opens only on your click, in a sandbox without access to this page. Tests in the repository pin each of these (page-safety.test.mjs, reader.test.mjs).
  • Regulation. The repository carries a compliance map generated from verified law (compliance map): personal data is not processed by the page, and the one generative feature is the optional studio generator.
  • Nothing hidden. The build sits in named chunks any PNG tool lists; the picture's own data is never used to carry anything. That is a rule of the format, enforced by its tests.

Deployment and roll-out. Use this page as it is, or host the two HTML files on your own origin — they are static files. Put forge.mjs in a build step to seal what the build produces, and forge.mjs read in the step that receives it. The roll-out above starts with one file and one team.

Risks, answered straight.

  • A signature proves who signed, not that the file is right. The tier the build earns says only that it passes the sovereignty gate; whether its contents are true is still for people to judge, and no tool awards the top tier.
  • The build is not secret. Anyone who holds a card can read what it carries. Do not put anything confidential in one; this is proof, not encryption.
  • Platforms strip and recompress pictures. Then the build is gone from that copy. The code printed on the card finds it again only for someone whose deck already holds the card; the sealed survival run on this page says how far that holds and where it stops.
  • Keys can be lost or misused. A lost key means new cards are signed by a new key, which you publish; a stolen one is a reason to publish that it no longer counts. Cards carry the signer's public key, so a team can always see which key signed what.
  • Device-to-device trade has been measured on one machine with two browser identities, not yet on two devices. That run waits on a second device and is on the record as not done.
  • An old browser without Ed25519 cannot check signatures. It says so, and does not open, keep or accept a signed card it could not check.

The case for the board. Files are where trust is hardest to keep: they are copied, edited and forwarded, and the record of what was approved usually lives somewhere else. The Forge puts the proof inside the file, so anyone can check it, anywhere, without asking anyone. It costs no licence and no server, the code is open and owned, every organ is mutation-tested on infrastructure we do not control, and a pilot needs one team and one recurring file. The question for the board is only which file to start with.

White paper · the card that carries its own proof

The problem. A file's history is not in the file. When a report, a build or a result is forwarded, edited or re-saved, the only way to know it is still the approved one is to ask the person who sent it, or a system that recorded it. Neither travels with the file.

The design. A card is a PNG that openly carries a single-file build in two declared text chunks, placed before the image's end marker, beside image data that is never changed (CARD-SPEC §2). The label records a seal — the sha256 of the compressed build — and is signed with Ed25519 over a canonical form in which the verifier puts the seal it computed itself, so one changed byte anywhere, build or label, fails the signature (§3.1). The card's tier is never written by its maker: it is earned by running the sovereignty gate on the build, and every reader runs it again (§5). The picture is drawn from the card's own tags, so it cannot contradict them (§4), and it prints the first 80 bits of the seal as a code a person or a camera can read (§7.1).

The trust argument. Nothing on a card is taken on the card's word. The seal is recomputed, the signature is checked against the recomputed seal, the tier is re-derived from the build, and a read of the printed code that could match two cards is refused rather than guessed. A stable process can still settle on a wrong reference; the reader's defence is to check the reference itself every time and to allow "I don't know" as an answer. That stance follows Gary W. Floyd's work on the Guided Entropy Principle (credited below).

What was measured. The printed seal was tested before it was trusted: a sealed survival run through platform-style damage, a paid read by a vision model, and the read rule that the kard-evolve creatures found, each sealed before it ran and published as it landed. The results are re-derived on this page by the same kernels, in The seal you can read, rather than typed here.

What it does not do. It does not keep a build secret, does not prove a build correct, and cannot bring back a stripped build for someone who never held the card. It never hides anything in the picture.
